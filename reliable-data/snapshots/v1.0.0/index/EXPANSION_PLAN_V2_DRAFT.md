## 三、`o_` 衔接节点重划的风险与处置（关键）

### 3.1 引用面实测

五个初中竞赛衔接节点 `o_div0`、`o_alg_skill`、`o_pigeon`、`o_dio`、`o_geo_basic`：

- **反向引用 17 条**：`j_alg → o_alg_skill`、`j_eq → o_dio`、`j_cong → o_div0`、`j_tri/j_simi/j_circle/j_trig → o_geo_basic`、`o_geo_ceva/o_geo_area → o_geo_basic`、`o_ineq/o_func_eq → o_alg_skill`、`o_cong/o_dio2 → o_dio/o_div0`、`o_comb_adv/o_graph → o_pigeon` 等。
- **文件占用 20+**：5 个节点的四类卡、manifest、差距矩阵、分批报告、素材 `nodes/lectures/themes/topic_index/content_meta.js`、`verify_content.js`、`build-reliable-data.js`、`HUMAN_SIGNOFF_V1.md`。
- **已入哈希**：这五个 ID 出现在 v1.0.0 的卡文件名、`pre`/`rel` 字段与 `content_hash` 计算输入中。

### 3.2 结论：重划 ≠ 改 ID，也 ≠ 改旧卡字段

**采用「逻辑重划、ID 与旧卡字节双冻结」**（家长 2026-11-25 确认零破坏方案后收紧）：

- 五个 `o_` 节点 **ID、文件名、卡内所有字段（含 `module` / `pre` / `rel`）全部保持字节不变**，v1.0.0 的 228 卡 `content_hash` 逐条不变。
- 草稿原写「改 `module` 归属 + 在 `pre` 接 `p_` 前置」会改动节点卡内容字段，**必然改变哈希**，与零破坏承诺冲突，故**废弃该做法**。
- 重划改由**独立映射文件**承载：`reliable-data/index/BRIDGE_MAP.md`（人读）+ `reliable-data/index/bridges.json`（机读）。在其中声明：五个节点的逻辑归属为「跨学段衔接（高小→初中→奥赛）」，以及 `p_` → `o_` 的衔接边（如 `p_div → o_div0`、`p_count → o_pigeon`、`p_geo → o_geo_basic`）。
- 效果一致（层级清晰、小学有出口、衔接显式），且旧卡零改动；下游若需把衔接边并入图谱，由 `build-data.js` 读 `bridges.json` 合成，不回写真源卡。

### 3.3 若坚持改 ID（不推荐，需家长明确授权）

- 必须重算全部 228 卡的 `content_hash`（因 `pre`/`rel` 字段变了），v1.0.0 与 v2.0.0 之间无法逐卡 diff。
- 需同步改 5 个脚本的硬编码 57、`build-data.js` 的生成预期、`verify_content.js` 的断言、`topic_index.js` 的引用。
- 需重写 `GAP_MATRIX.md` 与 `HUMAN_SIGNOFF_V1.md` 的回归点映射。
- **代价**：已发布的"修改走新版本、不覆盖旧版"仍在形式上成立，但追溯链断裂。故本草稿默认走 3.2 方案。
