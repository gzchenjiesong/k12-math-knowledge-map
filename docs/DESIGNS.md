## 主决策线：一次定位演进

图谱工具 → 主题视图 → 题型索引 → **授课优先**（当前生效）。前几步不是被推翻，而是层层降为辅助与验证层。演进顺序见 `IDX-007`。

### DSN-001: 以「来源」为主轴分层（确认稿 · 生效）

- **结论**：图谱纵向主轴用「初中课标 / 高中课标 / 奥赛四大板块」三来源，知识点作为横向网络。
- **为什么**：① 来源轴 = 进度轴，正值孩子「不知道当前进展」的首要痛点；② 来源自带难度与决策信号（同样是不等式，二次不等式 / 基本不等式 / 柯西排序分属三层，一眼可分课内外）；③ 来源是课标文本与竞赛大纲的客观可核对边界，学校大纲有出入时可直接对着增删节点。
- **被否方案**：直接按知识点组织——能回答「这是什么」，回答不了「我该不该现在会」。
- **补救机制**：每节点的前置依赖 / 关联标签可点击跳转 + 题目定位器，把散在三层的内容横向串起（图书馆式：书架按学科、主题索引卡跨架）。

### DSN-002: 增设「主题视图」（确认稿 · 生效）

- **结论**：双视图并存，主题视图按代数 / 几何 / 函数 / 数列 / 数论 / 组合等 10 大主题纵览；主题内按初中 → 高中 → 奥赛排序，来源降为节点标签。
- **为什么**：家长澄清集训队按小蓝本专题**跳跃式授课**，同一主题（如函数）散在三来源，课堂一次讲透、图谱里却分三处。主题视图还原专题的完整链条（如平面几何：全等→勾股→相似→圆→图形变换→梅涅劳斯/塞瓦→面积法→圆幂根轴→复数法）。
- **关键设计**：两视图共用同一掌握状态（`SPEC-003`、`RUL-003`），切换不丢进度；每节点仅归一个主主题，跨主题走前置 / 关联网络（`RUL-007`）。

### DSN-003: 题型索引反向层（确认稿 · 生效，现降为验证层）

- **结论**：新增 34 个题型的「题型 → 知识点 → 讲解」反向索引，题型卡四层：识别信号 / 关联知识点 / 切入方法 / 题型讲解。
- **为什么**：家长诊断——小蓝本是题集、几乎无讲解，同一知识点被拆成很多讲，孩子只能靠题型反推知识点，这是迷茫的最大根源。补这一层把散落各讲的同类题归为一类，点破「教材没讲的那部分」。
- **定位演进**：授课系统上线后，题型从「发现不懂」的工具降为「验证掌握」的环节（见 `DSN-004`），但功能保留。

### DSN-004: 授课优先重构（确认稿 · 当前生效）

- **结论**：APP 核心从检索 / 题型工具转为**专题授课系统**；授课为第一 tab，题型退到验证环节。
- **为什么**：家长核心诉求是补齐知识点讲解——「知识掌握牢靠后再去小蓝本按题型巩固没问题；知识体系不够时直接做题发现不懂是本末倒置；做对一道题 ≠ 掌握知识点，可能只掌握了题型」。
- **教育学依据**：奥苏贝尔「先行组织者」+ 布卢姆「掌握学习」——先给完整认知框架再进入练习。孩子「做对却没掌握」的本质是记住题型特征、没把知识挂到体系上。
- **专业补强**：纯讲解会产生「假性理解」（听懂 ≠ 真懂），故每知识点配「概念自检」问题（问「为什么」，非刷题），确认真理解。
- **被否方案**：以题型检索为主线（曾作为核心，本轮降级）；纯题海反推（本末倒置，明确否定）。

### DSN-005: 版权边界与内容策略（确认稿 · 生效）

- **结论**：APP 不内嵌任何有版权的书籍内容，全部讲解 / 例题原创编写；拥有正版文件的用户自行导入。
- **考据**：正版数字化渠道 —— 微信读书（《奥数教程》第七版、单墫作品、小丛书第三版）、华东师大「帮你学」App 电子书专区、京东 / 当当、公共图书馆数字资源。
- **被否方案**：网盘打包 / 盗版站 PDF —— 侵权，且扫描版无文本层仍不可搜，解决不了真实痛点。
- **红线**：见 `SPEC-004`。数学定理 / 公式 / 方法 / 竞赛真题题目属公共知识，可原创编写；作者原创讲解段落与解析文字不复制。

### DSN-006: 云服务降级为本地存储（确认稿 · 生效）

- **结论**：走本地实现，掌握进度与笔记存手机本地；数据层隔离在 `apps/miniprogram/utils/store.js`。
- **经过**：用户选择云端保存，但云服务 activate 确认弹窗被关闭，系统返回本地实现授权，遂按规范继续本地实现并如实说明。
- **代价 / 后手**：进度不能跨设备同步；日后想同步只需替换 `store.js`（`SPEC-003` 保证无第二数据源），页面不受影响。

### DSN-010: 内容保真三层机制（确认稿 · 生效）

- **结论**：内容正确性用「可机检断言 + 证据可见 + 人工闸门」三层保障，明确保留"AI 不能自证"的边界（见 `SPEC-008`、`RUL-008`）。
- **为什么**：家长指出内容是项目命门——「时效性、真实性、正确性最重要，出错整个程序失去意义甚至负效果」。R2 轮全量扫描果然查出实质错误（费马定理漏条件、几何例题缺结论），证实风险真实存在，且现有 `validate.js` 完全不覆盖内容。
- **三层设计**：
  1. **可机检层**：`verify_content.js` 只覆盖能机械判定的四类子集（数值复算 / 定理条件关键词 / 结论存在性 / 跨文件一致性），22 条断言。它的 PASS 只说明"没发现可判定错误"，不说明"内容正确"。
  2. **证据可见层**：`content_meta.js` 给每条讲解标注来源、证据等级（A/B/C）与复核状态（pending/checked/verified/disputed），授课页首屏展示，用户可一键标记存疑。把"不确定性"从隐藏变可见。
  3. **人工闸门层**：`verified` 只能由人对照权威资料签核，AI 禁止自证（`SPEC-008`）。这是最后也是唯一能真正保证正确性的环节。
- **被否方案**：①「让 AI 再复核一遍 AI 写的内容」——同源模型共享盲点，自证无效，明确否定；②「等全部内容人工审完再交付」——不现实，改为分层标注 + 渐进复核，未核的诚实标 `pending`；③「用大模型逐条打分判正确性」——打分是主观判断不是证据，不采信。
- **根本界限（如实告知用户）**：本机制能显著降低错误率，**但无法保证零错误**。最终权威仍是学校集训队讲义与权威教材；APP 定位为辅助讲解，不是教科书替代品。见 `PRM-009`。

### DSN-011: 进度同步改用微信云开发（确认稿 · 生效，自建服务器降级为备选）

- **结论**：跨设备进度同步采用微信云开发数据库（`progress` 集合），自建服务器 `deploy/server/` 保留代码但降级为备选方案。
- **为什么**：用户进度仅几 KB、要求「本地优先 + 离线可用 + 先预览发布」。云开发按 `_openid` 原生隔离、免 AppSecret / HTTPS / 域名白名单 / SSH 私钥，正好对口；自建服务器那条链路的 openid 隔离、token 签发、原子写都是重复造轮子，且这些运维成本在当前阶段是纯负担。
- **推进过程**：用户最初选自建服务器（腾讯云 CVM + 域名 + 私钥），并已搭好 `deploy/server/`；了解到云开发能力后修订为云开发优先。这是对既往决策的一次显式修订，故单独记录。
- **关键取舍**：
  1. 环境 ID（`k12-math-knowledge-map-dfac0f85a`）非凭证、官方文档即在前端明文，故可入库；不引入新的敏感配置项。
  2. 集合权限必须「仅创建者可读写」，靠 `_openid` 隔离；用户曾误提供 `xxx.cloudbase-ai-toolkit`（CloudBase AI Toolkit 资源标识，非环境 ID），已用 `cloud_env_list` 核实排除，未写入代码。
  3. 同步层 `utils/sync.js` 只替换传输实现，本地优先 / 合并策略 / 离线降级三条约束不变（`store.js` 仍是唯一状态源，`SPEC-003` 未破）。
  4. 无长期运营决策前不切腾讯云；云开发免费额度到期或需走出微信生态时，再启用 `deploy/server/`。
- **已验证**：`cloud_env_list` 确认环境有效、`progress` 集合创建成功且 `_openid` 索引就绪；运行时写入测试文档自动携带 `_openid`、可读回，隔离机制生效；编译无 console 错误；`validate 28/28`、`verify_content 22/22`。见 `CNF-012`。
