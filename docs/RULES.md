# RULES · 规则（系统怎么运转）

> 装：状态流转、判定顺序、职责边界、公式 / 结构。回答「要什么 / 怎么转」。
> 不装：当前取值（只引用 `CNF-NNN`）、不可违反的红线（归 `SPECS.md`）、历史理由（归 `DESIGNS.md`）。
> 带「修订 RN」的条目以最后一次修订为准，原文保留。

### RUL-001: 掌握状态三态流转

修订 R1（2026-11-24）。

节点掌握状态按 `CNF-002` 三态循环：未开始 → 学习中 → 已掌握 → 未开始。触发方式：详情页 / 授课页点按状态标签循环切换；图谱页长按节点切换。图谱节点点按进入详情、长按切状态，两动作分离。任何切换都写入 `SPEC-003` 指定的唯一数据源，切换视图不清零。

### RUL-002: 授课六段式结构

每个知识点的授课内容按固定六段展开：① 知识本质 → ② 核心方法与思维 → ③ 讲解型例题 → ④ 易错点 → ⑤ 知识连接 → ⑥ 概念自检。判定顺序不可调换。例题解答与自检答案默认折叠，先让孩子自己想。专题内知识点按「初中 → 高中 → 奥赛」递进排序，呈现从基础到竞赛的深化链。字段与完整性要求见 `CNF-007` 基准与 `TST-006`。

### RUL-003: 双视图状态同步

来源视图（初中课标 / 高中课标 / 奥赛）与主题视图（10 大主题）是同一批节点的两种切分（见 `DSN-001`、`DSN-002`）。两视图共用 `SPEC-003` 的唯一状态源，节点 ID 是共同主键；切换视图不丢进度。判定：在任一视图切换状态后，另一视图读到的必须是同一值（`TST-010`）。

### RUL-004: 题型与知识点双向索引

正向：题型卡列出关联节点，可跳知识点详情。反向：知识点详情列出「常考题型」，点击经 `globalData.focusTopic` 跳题型页并自动展开对应题型卡（数据结构见 `CNF-006`）。主题标签跳转经 `globalData.focusTheme`。跳转落地后必须清空 focus 标记，避免重复触发。

### RUL-005: 内容分批填充

新内容按 nodeId 或题型 ID 追加到 `apps/miniprogram/data/cards.js` / `apps/miniprogram/data/lectures.js` / `apps/miniprogram/data/topic_index.js` 的对应结构，不改动页面代码（页面只读数据）。追加后必须重跑覆盖断言 `TST-005`、`TST-009`，并在 `CNF-006` 更新覆盖度、在变更记录 `IDX-006` 留痕。数据文件结构与字段见 `CNF-005`。

### RUL-006: 交付校验流程

每轮改动按 `IDX-004` 完成类型同步后，运行 `node tests/validate.js` 执行文档四类校验，并逐条跑 `TESTS.md` 的 `TST-NNN`（自动化）与 `VFY-NNN`（环境验收）。统一输出 `RESULT=<通过数>/<总数> FAILED=<失败数>` 与 `VERDICT=PASSED|FAILED|BLOCKED_NO_EVIDENCE`。存在 `FAIL` / `BLOCKED` / 未解释的 `UNCOVERED` 不得判整体通过。证据不足显式判阻塞，不得出现「0 项检查 = 通过」。

### RUL-007: 两条正交切分轴

来源轴（进度轴）与主题轴（专题轴）正交：每个节点有且仅有一个来源、一个主主题。来源轴回答「我该不该现在会」，主题轴回答「这个专题有哪些内容」。跨主题联系不复制节点，走 `nodes.js` 的前置 / 关联网络。判定：主题分类须 57 节点全覆盖、无重复、无悬空引用（`TST-007`）。

### RUL-008: 内容复核状态流转与人工闸门

内容可信度由两条独立的轴描述，不得混为一谈：`CNF-002` 三态是「孩子会不会」，本节复核状态是「内容对不对」。

**复核状态四态**（取值见 `CNF-010`）：`pending`（待人工复核，默认）→ `checked`（做过实质核查 / 复算）→ `verified`（权威来源逐条核对通过）→ `disputed`（发现存疑，用户可随时标记）。判定顺序：

1. 新写 / 改写的讲解与例题，复核状态一律先置 `pending`。**禁止生成即标 `verified`**。
2. 通过 `verify_content.js` 的机械断言（`TST-013`~`015`），最多可升到 `checked`——因为机械校验只证明「可判定部分没矛盾」，不证明讲解正确。
3. 只有人（家长 / 老师 / 孩子对照学校讲义或权威教材）逐条核对后，才可置 `verified`，并记录核对人与日期（`CNF-010`）。AI 不得自行置 `verified`（`SPEC-008` 不自证红线）。
4. 任何人发现错误 → 标记 `disputed` → 走 `RUL-009` 纠错闭环。标记写入 `store.js` 的 disputed 字段，不新增数据源（`SPEC-003` 精神）。

**人工闸门清单**（每轮交付前至少抽检，执行记录进 `VFY-004`）：① 定理条件是否齐全；② 例题数值是否算对；③ 问「求 X」是否给了结论；④ 讲解口吻是否有把方法论说成硬结论。抽检发现 1 处错误，该专题全部降回 `pending` 并重跑内容校验。

### RUL-009: 内容纠错闭环

发现内容错误按固定五步，缺一不可：① 在 `BUGWALL.md` 登记缺陷（现象 / 根因 / 修法），取 `BUG-NNN`；② 修复 `apps/miniprogram/data/lectures.js` / `content_meta.js` 对应内容；③ 在 `verify_content.js` 补一条**针对性回归断言**（同类错误必须被自动抓到）；④ 把受影响节点的复核状态降回 `pending`（见 `RUL-008`）；⑤ 重跑 `TST-013`~`015` + `validate.js`，在 `IDX-006` 变更记录留痕。R2 轮发现的三处问题（BUG-009 / BUG-010 / BUG-011）即按此闭环处理，可作为范例。禁止「只改内容不补断言」——那会让同类错误再次发生。
